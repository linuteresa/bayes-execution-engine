## Recovery and retention

`JOB_STORE=sqlite` uses a local SQLite database with transactional dispatch and feedback. It supports multiple processes on one host; do not put its database on NFS or use it as a cross-host database. `JOB_STORE=redis` uses shared transactional metadata and dispatch/retention indexes. Persistent graph state independently requires `CHECKPOINTER=redis` or `postgres`.

The default `CHECKPOINTER=memory` survives within one process. After a process restart, its missing snapshots cause the pure model workflow to retry from the original prompt under a fresh attempt. A missing exact reference in a configured persistent saver returns an explicit error instead of silently choosing another checkpoint. Once a terminal result commits, memory snapshots are deleted because polling and feedback use the stored result. Persistent snapshots are deleted when the terminal job expires.

A new ownership token and physical checkpoint thread are allocated for every claim. A saver write and job-store write cannot share a transaction, so the saver first writes the attempt's snapshot and then publishes its exact address under an unexpired ownership check. Recovery copies only that published full checkpoint into a new attempt. Unpublished late snapshots and pending task writes do not become recovery input. This provides restart/retry semantics for the current model-only workflow; future tools with external side effects require their own idempotency contracts.

Defaults are a 16,000-character prompt, 128 active/pending jobs, 8 workers, 30-second leases, a 300-second run deadline and 86,400-second terminal retention. Model/sample/context budgets are configured separately in `.env.example`. Terminal results and their feedback events expire; aggregate learned context counts remain. A pathologically delayed backend write that finishes after its whole job has already expired can leave an unreferenced saver object; physical backend TTL/maintenance is appropriate for long-lived external saver deployments.
